# Fix Structured Logging

## Purpose

Find C# logging calls that do not use structured message templates.

Support two modes:

- `audit`: Find and report problems without changing files.
- `fix`: Find problems, apply safe fixes, and build the affected solution.

Interpret `$ARGUMENTS` as follows:

1. The first argument is the mode: `audit` or `fix`.
2. Any remaining argument is the file, folder, project, or solution scope.
3. If no mode is supplied, use `audit`.
4. If no scope is supplied, inspect the entire current repository.

Before starting, read the applicable `CLAUDE.md` files and follow all project-specific instructions.

## Supported logging APIs

Inspect logging calls that use:

- `Microsoft.Extensions.Logging.ILogger`
- `ILogger<T>`
- Serilog's static `Log` class
- Serilog's `ILogger`
- Existing project-specific logger wrappers when their method signatures are clear

Look for these common methods:

- `LogTrace`
- `LogDebug`
- `LogInformation`
- `LogWarning`
- `LogError`
- `LogCritical`
- `Verbose`
- `Debug`
- `Information`
- `Warning`
- `Error`
- `Fatal`

Do not treat `Console.WriteLine`, ordinary interpolated strings, or non-logging methods as logging violations.

## Files to inspect

Inspect C# files ending in `.cs`.

Exclude:

- `bin`
- `obj`
- `.git`
- `node_modules`
- generated files ending in `.g.cs`
- generated files ending in `.designer.cs`
- generated files containing an `<auto-generated>` header

Do not modify generated code.

## Patterns to find

Find logging calls using any of these patterns:

### String interpolation

```csharp
_logger.LogInformation($"Processing cuisine {cuisineId}");
```

### String concatenation

```csharp
_logger.LogWarning("Invalid cuisine: " + cuisineId);
```

### `string.Format`

```csharp
_logger.LogInformation(
    string.Format("Processing cuisine {0}", cuisineId));
```

### Positional placeholders

```csharp
_logger.LogInformation(
    "Processing cuisine {0}",
    cuisineId);
```

### Dynamically constructed templates

```csharp
string message = "Processing " + cuisineId;
_logger.LogInformation(message);
```

Dynamic templates should be reported for manual review unless the intended static template and argument list are unambiguous.

## Required output style

Use a static message template and pass values as separate arguments.

### String interpolation conversion

Before:

```csharp
_logger.LogInformation(
    $"Processing cuisine {cuisineId}");
```

After:

```csharp
_logger.LogInformation(
    "Processing cuisine {CuisineId}",
    cuisineId);
```

### String concatenation conversion

Before:

```csharp
_logger.LogWarning(
    "Invalid cuisine: " + cuisineId);
```

After:

```csharp
_logger.LogWarning(
    "Invalid cuisine: {CuisineId}",
    cuisineId);
```

### Exception conversion

Before:

```csharp
_logger.LogError(
    ex,
    $"Failed to process cuisine {cuisineId}");
```

After:

```csharp
_logger.LogError(
    ex,
    "Failed to process cuisine {CuisineId}",
    cuisineId);
```

Preserve the exception argument and its position.

### Event ID conversion

Before:

```csharp
_logger.LogWarning(
    eventId,
    $"Visitor {visitorId} was not found");
```

After:

```csharp
_logger.LogWarning(
    eventId,
    "Visitor {VisitorId} was not found",
    visitorId);
```

Preserve the EventId argument.

### Format specifier conversion

Before:

```csharp
_logger.LogInformation(
    $"Completed in {elapsedMilliseconds:N0} ms");
```

After:

```csharp
_logger.LogInformation(
    "Completed in {ElapsedMilliseconds:N0} ms",
    elapsedMilliseconds);
```

Preserve valid format specifiers.

## Placeholder rules

Use meaningful PascalCase placeholder names.

Examples:

- `userId` becomes `{UserId}`
- `cuisineId` becomes `{CuisineId}`
- `elapsedMilliseconds` becomes `{ElapsedMilliseconds}`
- `request.Id` becomes `{RequestId}`
- `response.StatusCode` becomes `{StatusCode}`
- `file.Name` becomes `{FileName}`

Do not use meaningless placeholders such as:

- `{Value}`
- `{Data}`
- `{Item}`
- `{Arg0}`

Use a generic name only when no meaningful name can be determined.

The number and order of placeholders must match the number and order of arguments.

## Safety rules

Do not change:

- logging levels
- application behavior
- exception handling
- EventId values
- control flow
- return values
- method signatures
- unrelated formatting
- unrelated code

Do not add new logging statements unless necessary to preserve an existing message.

Do not convert constant messages that have no variable values.

This is already valid:

```csharp
_logger.LogInformation("Application started");
```

Do not change it to an interpolated string.

Do not automatically log values that appear sensitive, including:

- passwords
- access tokens
- refresh tokens
- API keys
- secret keys
- connection strings
- authentication cookies
- authorization headers
- personal identification values

Report sensitive logging candidates instead of automatically modifying them.

Do not automatically use Serilog destructuring syntax such as `{@Request}` unless the surrounding project already uses that convention and the change is clearly appropriate.

Avoid changing custom logging wrappers when their overload behavior is uncertain. Report them for manual review.

## Audit mode

When running in `audit` mode:

1. Do not modify any file.
2. Search all files in the requested scope.
3. Report each problem with:
   - file path
   - line number
   - current code
   - recommended replacement
   - reason
4. Group the results into:
   - safe automatic fixes
   - manual-review items
5. Report the total:
   - files scanned
   - violations found
   - safe fixes
   - manual-review items

## Fix mode

When running in `fix` mode:

1. Inspect the requested scope.
2. Apply only high-confidence structured-logging fixes.
3. Do not modify manual-review items.
4. Review the resulting diff.
5. Verify that placeholders and arguments match.
6. Run `git diff --check` when the repository uses Git.
7. Follow the build instructions from `CLAUDE.md`.
8. If no build instructions exist:
   - locate the relevant `.sln` or `.csproj`;
   - run `dotnet build` on the narrowest appropriate solution or project.
9. Do not commit the changes.
10. Do not suppress CA2254 or other logging analyzer warnings.

## Final report

After completing the task, report:

- scope inspected
- files scanned
- files changed
- logging calls changed
- manual-review items
- build command used
- build result
- any remaining logging analyzer warnings
- a concise summary of the Git diff
